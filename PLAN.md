# speclint — план

Детерминированный линтер согласованности спецификаций для SDD-репозиториев (spec-driven development). Проверяет весь корпус спек, а не одну фичу: висячие ссылки, конфликты изменений, реестр решений, покрытие сценариев тестами — в одном репозитории, в монорепо и между репозиториями.

Документы: [docs/requirements.md](docs/requirements.md) (ТЗ), [docs/architecture.md](docs/architecture.md).

## Активная ветка

Нет — M0–M14 влиты в `main`. Осталось за пользователем: публикация (GitHub, npm) и прогон на рабочем проекте.

## Стек

- TypeScript, Node ≥ 20, пакет npm `@haliksar/speclint`, запуск `npx @haliksar/speclint`.
- Тесты — Vitest 4 (D14).
- Без вызовов модели и без сети во время проверки.

## Решения (зафиксированы)

| # | Решение | Почему |
|---|---|---|
| D1 | Ядро работает с нейтральной моделью (требование, сценарий, решение, изменение, ссылка, тест с адресом); форматы читают адаптеры. Первый и пока единственный адаптер — OpenSpec | Проверки от формата не зависят; Spec Kit, Kiro и `.req` из Clear подключаются позже без переделки правил |
| D2 | Имя нейтральное: `speclint`, пакет `@haliksar/speclint` (имя `speclint` в npm занято) | Инструмент не привязан к OpenSpec |
| D3 | Все правила детерминированы, моделей нет | Ниша: Spec Kit `/analyze` проверяет одну фичу и через модель; линтер должен работать одинаково и в CI без агента, и как быстрая обратная связь агенту |
| D4 | Контракт CLI взят из Clear `req/cli`: коды 0 — чисто, 1 — есть находки, 2 — сломан запуск; `--format text|json`; стабильные латинские ID правил | Проверен в Clear; JSON одинаково читают CI и агенты |
| D5 | Адрес — `[пространство:]capability/requirement#scenario`. До M5 внешние адреса (с пространством) не ошибка, а отметка «не проверено» | Мультирепо заложено в формат адреса с первой версии и не ломает её |
| D6 | Мультирепо — через опубликованный манифест спек с фиксацией версий (как lock-файл); соседние чекауты не нужны | На рабочем проекте репозитории независимы и связаны только опубликованными артефактами — и у разработчика, и в CI |
| D7 | Покрытие в две ступени: M4 — адрес-метка в любом тестовом файле (не зависит от языка); M6 — дословные шаги сценария среди строковых литералов теста | На рабочем проекте тесты на Kotlin/Java, TypeScript/JS, Swift и Python |
| D8 | Полигон — рабочий проект пользователя с M2: каждая веха обкатывается на нём, speclint только читает файлы локально | Замер пользы на реальном пользователе, которого не было у Noggin и Clear |
| D9 | Не повторять ошибок Clear и Noggin: свой формат, обещания без кода, методология раньше пользователей, монолит | Итоги Noggin M18 и изучения Clear (2026-10-24) |
| D10 | Адрес требования и сценария — слаг имени (NFC, нижний регистр, не-буквы → `-`, кириллица сохраняется); ссылка на старый слаг после RENAMED — ошибка с подсказкой нового адреса; совпадение слагов — ошибка `address-collision` (Q1) | В OpenSpec ID нет, только имя; явный ID в заголовке чужд OpenSpec и ломается в MODIFIED/RENAMED |
| D11 | Одна разметка ссылки везде — токен `spec:<адрес>` в Markdown корня и в тестах на любом языке (Q2, Q4) | В OpenSpec разметки ссылок нет; один лексер на все файлы, не зависит от языка тестов |
| D12 | speclint не повторяет проверки `openspec validate` внутри одного изменения; M1 проверяет изменения между собой и по корпусу ошибкой (то, что OpenSpec отдаёт как INFO) | Ниша — согласованность корпуса; повтор validate расходился бы с ним по мере обновлений OpenSpec |
| D13 | Код `1` — только при находке уровня `error`; предупреждения и info дают `0` | Так в Clear `req/cli`; предупреждение не должно ронять CI |
| D14 | Vitest 4, TypeScript 7 | Vitest 5 требует Node ≥ 22.12, а поддерживаем Node ≥ 20 |
| D15 | Дельта в модели несёт сценарии своего блока (`Delta.scenarios`); адрес в `Reference` — строка, разбирает правило; адаптер отдаёт `Corpus` со списком capability | Без сценариев дельты не разрешить `#сценарий` из изменения; разбор адреса зависит от набора capability в картине изменения |
| D16 | Текстовый отчёт: `файл:строка: уровень правило: сообщение` по строке на находку, затем итог; `related` — только в JSON | Формат компиляторов, кликабелен в IDE и терминале |
| D17 | `summary.files` — число файлов, прочитанных адаптером | Контракт M0 не уточнял, что считать |
| D18 | Токен `spec:` не считается, если перед ним буква, цифра, `_` или `-`, и если адрес пустой; блоки кода не исключаются | На `Fission-AI/OpenSpec` встречаются `openspec:archive`, `Bash(openspec:*)`, «each spec:» |
| D19 | `delta-overlap` — предупреждение на каждой из пересекающихся дельт; ключ — capability и точное имя (для RENAMED — FROM) | Каждый автор изменения видит конфликт в своём файле |
| D20 | Подсказка по RENAMED для ссылки берёт переименования архивных изменений и своего изменения, но не чужих открытых | Для ссылки вне изменения старое имя ещё действует, пока изменение открыто |
| D21 | Несколько корней — только через `roots` в `speclint.json`; автопоиска `openspec/` нет; с конфигурацией `<путь>/openspec` не подразумевается; `space` у корня обязателен и уникален | Решение пользователя; вендорные и чужие `openspec/` (например в `node_modules`) не попадают в проверку |
| D22 | Каждый корень проверяется правилами M1 отдельно; `spec:<space>:…` с пространством локального корня разрешается в его основных спеках, подсказки — из его изменений | Изменение одного корня не правит спеки другого; одинаковые capability в разных корнях не конфликтуют |
| D23 | `/` перед `spec:` тоже исключает токен (дополнение D18) | Ложное срабатывание на URL `…/spec:…` в полевом прогоне M2 |
| D24 | Решения — `<корень>/decisions/<id>.md`, id — имя файла; front-matter `status`, `superseded-by` (id того же корня); обоснование — раздел `## Rationale`/`## Обоснование`. Необязательны (Q3) | Решение пользователя: работает по пространствам M2 без новых настроек, общий реестр M5 — ещё одно пространство; дубликат id невозможен |
| D25 | `Decision.status` — строка из файла, `rationale: boolean`; правка черновика M0 | Адаптер не выдаёт находок, неверный статус — правило |
| D26 | Ссылки из файлов `decisions/` на неактивные решения не дают `decision-inactive-ref` | Решение пользователя: реестр ссылается на свою историю («заменяет …») |
| D27 | Ошибки реестра — `decision-status-invalid`, `decision-supersede-missing`, `decision-supersede-cycle` (error), на строке 1 файла; `decision-duplicate` не нужен (D24) | Пользователь поручил выбрать |
| D28 | Тестовые файлы — по конвенциям Kotlin/Java, TS/JS, Swift, Python; `tests` в `speclint.json` заменяет конвенции целиком; dot-папки, `node_modules`, `build`, `dist`, `out`, `target`, `Pods`, `Carthage`, `DerivedData`, `venv`, `__pycache__` не читаются никогда | Решение пользователя: запуск без настройки; пропуск папок — производительность и вендорный код |
| D29 | Метка без пространства — в корне, чья родительская папка — ближайший предок теста; один корень — все тесты его; тест вне корней без пространства — `test-ref-dangling` | Решение пользователя: в монорепо тест лежит рядом со своими спеками |
| D30 | Метка требования покрывает все его сценарии; метка capability — не покрывает | Решение пользователя, как в Clear `trace`; про capability — минимум, не спрашивалось |
| D31 | Метка видит основные спеки и все открытые изменения; `scenario-untested` — только для основных спек | Решение пользователя: тест пишут до архивации, а требовать его до архивации рано |
| D32 | `test-ref-dangling` — любая неразрешённая метка (висячая, архив, неактивное решение) с сообщением как у ссылки; внешний адрес — `ref-external-unchecked` | Поручение M4: «включая заменённые решения и архив» |
| D33 | `TestMark.address` — строка, `TestMark.root` — корень-владелец или `null` (правка черновика M0); `summary.files` включает тестовые файлы (дополнение D17) | Как D15 для ссылок; владелец нужен правилам |
| D34 | Q5: потребитель коммитит копию манифеста зависимости в свой репозиторий и фиксирует версию в `dependencies`; speclint читает только локальный путь; публикация у поставщика — любым его артефактом; команды скачивания нет | Решение пользователя: любой стек (Kotlin, Swift, TS), без сети, diff копии виден в PR как lock-файл |
| D35 | `speclint manifest [путь] --release <версия>` печатает манифест в stdout; версия — только из флага; корень без пространства — код `2` | Решение пользователя: версию знает CI релиза (тег), не зависит от стека; `--version` уже занят |
| D36 | Манифест: `speclint: 1`, `version`, `roots` (по корню: `space`, `capabilities`, `requirements` — активные со сценариями и `covered` плюс история `removed`/`renamed`, `changes` — id и `archived`, `decisions`), `marks` — метки на чужие пространства; массивы по кодовым точкам; требования открытых изменений не публикуются. Правка черновика M0: `roots` вместо одного `space` | Все корни M2 в одном манифесте; история нужна для `ref-archived` и подсказок RENAMED; `marks` — для покрытия «клиент и сервер» |
| D37 | `dependencies.<space>` — `{ manifest, version }` или `{ unchecked: true }`; не объявлено, нет файла или пространства в файле — `dependency-missing` у ссылки или метки; не JSON, формат не `1`, версия не та — код `2` | Решение пользователя про `unchecked`; остальное — по контракту M0 |
| D38 | Внешние ссылки и метки — тем же кодом, что локальные, над корпусом из манифеста; сообщение + `; зависимость <space> <version>`, `related` пуст; `summary.files` считает манифесты | «Теми же правилами» из чек-листа; строк в манифесте нет |
| D39 | `scenario-untested-anywhere` — все известные сценарии (свои и зависимостей); покрытие — свои метки, `covered` и `marks` манифестов; при загруженном манифесте заменяет `scenario-untested`; сценарий зависимости — на файле манифеста, строка `null` | Решение пользователя |
| D40 | Шаг сценария — строка тела с `GIVEN`/`WHEN`/`THEN`/`AND`/`BUT` (заглавными) после снятия маркера списка, `**` и пробелов по краям; сравнивается с ключевым словом, точно, с литералом после обрезки краёв; при промахе — «похожая строка» без учёта регистра, `ё/е` и повторных пробелов | Решение пользователя; образец — Clear `trace`. С ключевым словом литерал однозначно читается как шаг, короткие шаги не совпадают случайно |
| D41 | Один лексер литералов, режим по расширению (Python, JS/TS, Kotlin/Java/Swift); раскрываются `\"`, `\'`, `\\`, `` \` ``; f-строки, интерполяция, `r`-строки Python и сырые строки Swift — как написаны; незакрытая однострочная строка отбрасывается до конца строки; имена в обратных кавычках Kotlin/Swift — не литералы; регулярные выражения JS/TS — эвристика по предыдущему символу; вложенные шаблоны внутри `${…}` отложены | Решение пользователя («всё как текст»); regex и вложенные шаблоны — по полевому прогону на `microsoft/vscode` |
| D42 | Литералы всех тестовых файлов с меткой сценария или его требования складываются; метка требования требует шаги всех его сценариев; предупреждение — на строке сценария по одному на шаг, `related` — метки; сценарии открытых изменений не проверяются | Решение пользователя (как в Clear `trace`); ближайший тест-метод требует разбора кода в четырёх языках — отложен; открытые изменения — как D31 |
| D43 | Манифест формата `2`: у сценария `steps`; читаются форматы `1` и `2`, по `1` шаги зависимости не сверяются; `speclint manifest` печатает `2` | Решение пользователя: версия формата говорит, несёт ли манифест шаги |
| D44 | Лексер читает только тестовые файлы с меткой | Производительность: худший случай на vscode 1,8 с против 1,2 с в M4 |
