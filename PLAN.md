# speclint — план

Детерминированный линтер согласованности спецификаций для SDD-репозиториев (spec-driven development). Проверяет весь корпус спек, а не одну фичу: висячие ссылки, конфликты изменений, реестр решений, покрытие сценариев тестами — в одном репозитории, в монорепо и между репозиториями.

Документы: [docs/requirements.md](docs/requirements.md) (ТЗ), [docs/architecture.md](docs/architecture.md).

## Активная ветка

`feat/m0-contracts` — веха M0 (контракты), не начата.

## Стек

- TypeScript, Node ≥ 20, пакет npm `@haliksar/speclint`, запуск `npx @haliksar/speclint`.
- Тесты — Vitest (выбор окончательно фиксируется в M0).
- Без вызовов модели и без сети во время проверки.

## Решения (зафиксированы)

| # | Решение | Почему |
|---|---|---|
| D1 | Ядро работает с нейтральной моделью (требование, сценарий, решение, изменение, ссылка, тест с адресом); форматы читают адаптеры. Первый и пока единственный адаптер — OpenSpec | Проверки от формата не зависят; Spec Kit, Kiro и `.req` из Clear подключаются позже без переделки правил |
| D2 | Имя нейтральное: `speclint`, пакет `@haliksar/speclint` (имя `speclint` в npm занято) | Инструмент не привязан к OpenSpec |
| D3 | Все правила детерминированы, моделей нет | Ниша: Spec Kit `/analyze` проверяет одну фичу и через модель; линтер должен работать одинаково и в CI без агента, и как быстрая обратная связь агенту |
| D4 | Контракт CLI взят из Clear `req/cli`: коды 0 — чисто, 1 — есть находки, 2 — сломан запуск; `--format text|json`; стабильные латинские ID правил | Проверен в Clear; JSON одинаково читают CI и агенты |
| D5 | Адрес — `[пространство:]capability/requirement#scenario`. До M5 внешние адреса (с пространством) не ошибка, а отметка «не проверено» | Мультирепо заложено в формат адреса с первой версии и не ломает её |
| D6 | Мультирепо — через опубликованный манифест спек с фиксацией версий (как lock-файл); соседние чекауты не нужны | На рабочем проекте репозитории независимы и связаны только опубликованными артефактами — и у разработчика, и в CI |
| D7 | Покрытие в две ступени: M4 — адрес-метка в любом тестовом файле (не зависит от языка); M6 — дословные шаги сценария среди строковых литералов теста | На рабочем проекте тесты на Kotlin/Java, TypeScript/JS, Swift и Python |
| D8 | Полигон — рабочий проект пользователя с M2: каждая веха обкатывается на нём, speclint только читает файлы локально | Замер пользы на реальном пользователе, которого не было у Noggin и Clear |
| D9 | Не повторять ошибок Clear и Noggin: свой формат, обещания без кода, методология раньше пользователей, монолит | Итоги Noggin M18 и изучения Clear (2026-10-24) |

## Контракты

Фиксируются в M0 в [docs/architecture.md](docs/architecture.md): модель ядра, адрес, адаптер OpenSpec, JSON-отчёт CLI, формат манифеста.

## Вехи

### M0 — контракты (`feat/m0-contracts`)
- [ ] Разобрать реальный формат OpenSpec (последняя версия): `specs/`, `changes/` с дельтами, архив, как идентифицируются требования и сценарии, как ссылаются друг на друга
- [ ] Модель ядра и адрес (D5): как адрес строится из OpenSpec, что с переименованием
- [ ] JSON-отчёт CLI и список ID правил M1–M6
- [ ] Черновик формата манифеста (M5) и конфигурации (корни, зависимости)
- [ ] Каркас TS-проекта: сборка, тесты, `npx` запускается и печатает версию
- [ ] Ответы на открытые вопросы ниже или явный перенос

### M1 — ядро и адаптер OpenSpec (`feat/m1-core`)
- [ ] Адаптер OpenSpec → модель, один корень `openspec/`
- [ ] Висячие ссылки: ссылка на несуществующее требование, сценарий или изменение, на ушедшее в архив
- [ ] Конфликты дельт: MODIFIED/REMOVED — на существующее требование; ADDED не дублирует существующее; два открытых изменения трогают одно требование
- [ ] CLI по D4, сценарные тесты на фикстурах

### M2 — несколько корней (монорепо) (`feat/m2-roots`)
- [ ] Несколько папок `openspec/` в одном репозитории, ссылки между ними
- [ ] Первый прогон на рабочем проекте, запись находок и ложных срабатываний

### M3 — реестр решений (`feat/m3-decisions`)
- [ ] Решения со статусом (`действует` / `заменено X` / `отменено`) и обоснованием
- [ ] Ссылка на заменённое или отменённое решение как на действующее — ошибка; решение без обоснования — предупреждение

### M4 — покрытие по адресу (`feat/m4-coverage`)
- [ ] Адрес-метка сценария в тестах на Kotlin/Java, TypeScript/JS, Swift, Python
- [ ] Сценарий без теста — предупреждение; метка на несуществующий адрес — ошибка

### M5 — мультирепо (`feat/m5-manifest`)
- [ ] `speclint manifest`: манифест репозитория (требования, сценарии, решения, статусы, покрытие, версия)
- [ ] Зависимости с фиксацией версий; внешние ссылки сверяются с манифестом без сети
- [ ] Сводная проверка: сценарий фичи не покрыт ни в одном репозитории

### M6 — дословные шаги (`feat/m6-steps`)
- [ ] Шаги сценария дословно среди строковых литералов теста (общий лексер кавычек для четырёх языков, особые случаи по мере появления)

## Отложено

- Адаптеры Spec Kit, Kiro, `.req` из Clear — по запросу пользователей.
- Противоречия между сценариями и стоп-слова (есть в Clear `req check`) — после M6, если окупится.
- Открытие репозитория Clear как «следующей ступени» для Kotlin-команд — когда у speclint будут пользователи.

## Открытые вопросы

- Q1 В OpenSpec нет явных ID требований (заголовок `### Requirement: <имя>`): адрес из имени (слаг) или явный ID? Как переживать переименование?
- Q2 Как ссылаться на требование из текста спеки, дизайна и задач — какая разметка ссылки?
- Q3 Где хранить решения: `openspec/decisions/` или отдельная папка у корня; формат — front-matter?
- Q4 Вид адрес-метки в тестах для четырёх языков (имя теста, аннотация, комментарий).
- Q5 Как публиковать и получать манифест на рабочем проекте (npm, Maven, файл релиза)?
