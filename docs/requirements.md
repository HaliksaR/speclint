# speclint — требования

## Проблема

В большом проекте, который ведут люди и агенты, спецификации расходятся сами с собой и с кодом:

- ссылка указывает на требование, которого уже нет или которое заменено;
- два параллельных изменения правят одно и то же требование;
- действует решение, которое давно заменено другим;
- сценарий описан, но ни один тест его не проверяет;
- в мультирепо поставщик API изменил требование, а потребитель об этом не знает.

SDD-фреймворки (OpenSpec, Spec Kit, Kiro) помогают писать спеки, но не проверяют согласованность всего корпуса детерминированно.

## Пользователь

Первый пользователь — рабочий проект автора:

- спеки уже ведутся в OpenSpec;
- есть и монорепо с несколькими папками спек, и несколько независимых репозиториев;
- репозитории связаны контрактами API, общими библиотеками, общими решениями, фичами «клиент и сервер»; связь только через опубликованные артефакты;
- тесты на Kotlin/Java, TypeScript/JS, Swift, Python.

## Что делает

1. **Висячие ссылки** — ссылка на несуществующее или архивное требование, сценарий, изменение, решение.
2. **Конфликты изменений** — дельта правит или удаляет несуществующее требование, добавляет дубликат; два открытых изменения трогают одно требование.
3. **Реестр решений** — решения со статусом и обоснованием; ссылка на заменённое решение как на действующее — ошибка.
4. **Покрытие тестами** — у сценария есть тест (адрес-метка), позже — шаги сценария дословно в тесте.
5. **Мультирепо** — внешние ссылки сверяются с опубликованным манифестом зафиксированной версии.

## Нефункциональные требования

- Запуск `npx @haliksar/speclint` без настройки на репозитории OpenSpec.
- Детерминированность: без моделей и без сети во время проверки.
- Коды возврата 0/1/2 и JSON-отчёт для CI и агентов.
- Только чтение файлов проекта.

## Чего не делает

- Не судит смысл требований.
- Не генерирует код и спеки.
- Не заменяет OpenSpec: работает поверх его файлов.
