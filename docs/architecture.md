# speclint — архитектура

Контракты зафиксированы в M0. Формат OpenSpec, на котором они построены, — [openspec-format.md](openspec-format.md).

## Слои

```
адаптеры форматов  →  модель ядра  →  правила  →  отчёт (text | json)
(OpenSpec, позже       (требование,     (ссылки,
 Spec Kit, Kiro)        сценарий,        дельты,
                        решение,         решения,
адаптеры тестов    →    изменение,       покрытие)
(Kotlin/Java, TS,       ссылка, метка)
 Swift, Python, Go)
                        манифесты зависимостей (M5)
```

- Правила видят только модель ядра и не знают формата файлов.
- Каждый элемент модели знает свой корень и пространство — так несколько корней (M2) и внешние манифесты (M5) добавляются как источники данных без переделки правил.

## Модель ядра

```ts
type Root        = { path: string; space: string | null }
type Capability  = { root: Root; id: string; file: string }                     // id = "identity/user-auth"
type Requirement = { capability: Capability; name: string; slug: string; line: number; scenarios: Scenario[] }
type Scenario    = { name: string; slug: string; line: number; steps: string[] }
type Change      = { root: Root; id: string; archived: boolean; deltas: Delta[] } // id без даты архива
type Delta       = { change: Change; capability: string; op: "added" | "modified" | "removed" | "renamed";
                     requirement: string; to: string | null; file: string; line: number; scenarios: Scenario[] }
type Reference   = { address: string; file: string; line: number; change: Change | null }        // адрес как в тексте, разбирается правилами
type Corpus      = { root: Root; capabilities: Capability[]; requirements: Requirement[]; changes: Change[]; references: Reference[]; decisions: Decision[]; files: number }
type Decision    = { id: string; status: string; supersededBy: string | null; rationale: boolean; file: string }  // M3
type TestMark    = { address: string; root: Root | null; file: string; line: number }  // M4; root — корень-владелец теста
```

`Delta.scenarios` — сценарии блока ADDED/MODIFIED: без них не разрешить `#сценарий` в ссылке из изменения (D15). `Corpus` — всё, что адаптер прочитал из корня; `files` — число прочитанных файлов.

`Decision.status` — строка как в файле: адаптер не выдаёт находок, неверный статус ловит правило `decision-status-invalid` (D25). `rationale` — есть ли непустое обоснование.

`Scenario.steps` — непустые строки тела сценария как в файле; шагами для M6 считаются только строки с ключевым словом (см. [Шаги](#шаги-m6)).

`Reference` — ссылка из Markdown корня, `TestMark` — та же разметка в тестовом файле. `change` у ссылки — изменение, в чьей папке она лежит. Адрес метки — строка, как у ссылки (D15); `root` — корень, которому принадлежит тест, `null` — тест вне корней (D29, D33).

## Адрес (D5)

```
адрес        = [пространство ":"] цель
цель         = capability ["/" требование ["#" сценарий]]
             | "change/" id-изменения
             | "decision/" id-решения
capability   = сегмент {"/" сегмент}                  путь папки относительно specs/
требование   = слаг
сценарий     = слаг
пространство = [a-z0-9-]+
сегмент      = [\p{L}\p{N}_-]+
```

**Слаг** имени требования или сценария: Unicode NFC → нижний регистр → каждая серия символов не из `\p{L}\p{N}` заменяется на `-` → `-` по краям убираются. `Session Timeout` → `session-timeout`, `Тайм-аут сессии (idle)` → `тайм-аут-сессии-idle`.

**Разбор пути.** Capability — самый длинный префикс сегментов, который есть среди capability корня; остаток — ноль или один сегмент (требование). Иначе адрес висячий.

**Префиксы `change/` и `decision/`** зарезервированы: capability с таким первым сегментом не адресуется.

**Где ищется.** Без пространства — в своём корне. С пространством, совпадающим с пространством локального корня (M2), — в нём. С чужим пространством — по манифесту зависимости из `dependencies` (M5), см. [Манифест](#манифест-m5).

**Что считается существующим.** Ссылка из файла изменения X видит основные спеки с применёнными дельтами X (RENAMED → REMOVED → MODIFIED → ADDED, как архивация OpenSpec). Ссылка из любого другого файла видит только основные спеки. Требование, которое есть лишь в чужом открытом изменении, — висячая ссылка с указанием этого изменения в `related`.

### Разметка ссылки (Q2, Q4)

Один токен везде — в Markdown корня и в тестах на любом языке (в имени теста, аннотации, строке или комментарии):

```
spec:auth/session-timeout#idle-timeout
spec:billing:invoices/create
spec:change/add-2fa
```

Токен — `spec:` и адрес до первого символа, который в адрес не входит (буквы, цифры, `_ - / # :`). Перед `spec:` не должно быть буквы, цифры, `_`, `-`, `/` или `:`, а пустой адрес токеном не считается: `openspec:archive`, `Bash(openspec:*)`, «each spec: has», `https://example.com/spec:x`, `file:spec:x` — не ссылки (D18, D23, D47). Блоки кода не исключаются: токен везде один. Markdown ищется во всех `*.md` корня, кроме `changes/archive/**`: архив — история, ссылки в нём не проверяются.

### Переименование

Адрес строится из текущего имени, поэтому переименование требования меняет адрес. Ссылка на старый слаг — `ref-dangling`; если старый слаг есть в RENAMED FROM открытого или архивного изменения, сообщение называет новый адрес и изменение, а `related` указывает на строку RENAMED. Цепочки переименований прослеживаются до последнего имени.

Два требования одной capability (или два сценария одного требования) с одинаковым слагом — `address-collision`: адрес обязан быть однозначным.

## CLI (D4)

По образцу Clear `req/cli`:

```
speclint [путь] [--format text|json]
speclint manifest [путь] --release <версия>
speclint mutate [путь] [--scope префикс] [--budget N]
speclint impact [путь] [--diff <git-диапазон>] [--rebuild]
speclint init [путь]
speclint --version
```

- `init` (M15, D65) — `src/init.ts`: пишет `speclint.json`, `openspec/app/specs/example/spec.md`, `example_test.go` и печатает строку CI; если любой из файлов есть — код `2`, ничего не пишется.

- `impact` (M13, D61–D64) — `src/impact.ts`: строки изменения из `git diff -U0 --relative`; спеки → сценарии по заголовкам над строкой; тесты → метки, в теле теста которых строка (`TestMark.end` — конец тела, общий с D59); Go-код → тесты по карте покрытия `.speclint/coverage.json`, которую снимает `covered` из `src/mutate.ts` с `-coverpkg=<модуль>/...`. JSON: `{ tool, version, diff, contexts: [{ space, class, scenarios }], modules, scenarios: [{ address, reasons }], findings: [{ level, rule, message }] }`.

- `manifest` печатает манифест репозитория в stdout (M5, D35); без `--release` или с корнем без пространства — код `2`.

- `путь` — папка репозитория, по умолчанию текущая. Без конфигурации корень — `<путь>/openspec`; с `<путь>/speclint.json` — корни из `roots`, автопоиска нет (D21).
- Коды возврата: `0` — ошибок нет (предупреждения и info допустимы), `1` — есть хотя бы одна находка уровня `error`, `2` — сломан запуск: неизвестный флаг, неверное значение, нечитаемая конфигурация, корень не найден.
- `--version` печатает версию пакета и выходит с `0`.

### JSON-отчёт

```json
{
  "tool": "speclint",
  "version": "0.1.0",
  "status": "findings",
  "findings": [
    {
      "level": "error",
      "rule": "ref-dangling",
      "file": "openspec/changes/add-2fa/design.md",
      "line": 12,
      "message": "spec:auth/session-timout: требования нет в auth",
      "related": [{ "file": "openspec/specs/auth/spec.md", "line": 40 }]
    }
  ],
  "summary": { "errors": 1, "warnings": 0, "infos": 0, "files": 30 }
}
```

- `status` — `ok`, если ошибок нет, иначе `findings`; дублирует код возврата.
- `level` — `error | warning | info`. `file` — путь относительно аргумента `путь` через `/`; `file` и `line` — `null`, если находка не привязана к месту.
- Находки упорядочены по `file`, `line`, `rule` (сравнение по кодовым точкам) — отчёт детерминирован.
- `summary.files` — число прочитанных файлов: спеки, дельты открытых и архивных изменений, `*.md` корня вне архива, решения, тестовые файлы (D33).

### Текстовый отчёт

По строке на находку, затем итог (D16):

```
openspec/README.md:3: error ref-dangling: spec:auth/session-timout: требования нет в auth
speclint: ошибок 1, предупреждений 0, файлов 9
```

`related` в тексте не печатается — только в JSON.

## Правила

ID латинские, стабильные; уровень — по умолчанию.

| ID | Веха | Уровень | Что |
|---|---|---|---|
| `ref-dangling` | M1 | error | адрес не разрешается: нет capability, требования, сценария, изменения; при промахе в пределах двух букв — «похоже на spec:…» (M9, D53); тире в токене читается как дефис (D54) |
| `ref-archived` | M1 | error | ссылка на архивное изменение или на требование, удалённое архивным изменением |
| `address-collision` | M1 | error | два требования capability или два сценария требования дают один слаг |
| `delta-target-missing` | M1 | error | MODIFIED, REMOVED или RENAMED FROM на требование, которого нет в основной спеке и которое не добавляет ни одно другое открытое изменение |
| `delta-target-exists` | M1 | error | ADDED требования, которое уже есть в основной спеке |
| `delta-overlap` | M1 | warning | два открытых изменения трогают одно требование |
| `ref-external-unchecked` | M1 | info | пространство объявлено в `dependencies` как `unchecked` (с M5; до M5 — любой внешний адрес) |
| `decision-inactive-ref` | M3 | error | ссылка на заменённое или отменённое решение |
| `decision-no-rationale` | M3 | warning | решение без обоснования |
| `decision-status-invalid` | M3 | error | статус не `active`/`superseded`/`revoked`, `superseded` без `superseded-by` или `superseded-by` при другом статусе |
| `decision-supersede-missing` | M3 | error | `superseded-by` на решение, которого нет в корне |
| `decision-supersede-cycle` | M3 | error | цепочка замен возвращается к решению |
| `test-ref-dangling` | M4 | error | метка в тесте на несуществующий адрес |
| `scenario-untested` | M4 | warning | у сценария нет ни одной метки в тестах; в корне без единой метки — одна info на корень (M7) |
| `dependency-missing` | M5 | error | внешнее пространство не объявлено в `dependencies`, файла манифеста нет или в нём нет пространства |
| `scenario-untested-anywhere` | M5 | warning | сценарий не покрыт ни в одном репозитории, чьи манифесты известны; при загруженных манифестах заменяет `scenario-untested`, в том числе сводной info (M7) |
| `context-dependency-undeclared` | M10 | error | ссылка из корня с `uses` в пространство вне `uses` |
| `context-cycle` | M10 | error | цикл зависимостей контекстов в `uses` |
| `scenario-tested-by-text` | M11 | info | все тесты сценария читают исходники (`textChecks`) и ни один не проверяет поведение (`behaviourChecks`) |
| `scenario-duplicate` | M10 | warning | сценарий повторяет шаги более раннего сценария корпуса |
| `scenario-steps-missing` | M6 | warning | шага сценария нет дословно среди строковых литералов тестов с меткой сценария или его требования |

### Как работают правила M1

- **Видимость.** Для каждого открытого изменения строится своя картина: основные спеки + его дельты в порядке RENAMED → REMOVED → MODIFIED → ADDED. MODIFIED и ADDED приносят блок дельты целиком (имя, строку, сценарии), RENAMED сохраняет сценарии и место старого блока, дельта на новую capability создаёт её.
- **`ref-dangling`.** Разбор цели: capability — самый длинный префикс, затем ровно один сегмент требования и необязательный `#сценарий`. Если требования нет, по порядку: цепочка RENAMED архивных изменений и своего изменения → подсказка нового адреса, `related` — строки FROM; REMOVED архивного изменения → `ref-archived`; цель разрешается в картине чужого открытого изменения → «есть в открытом изменении X», `related` — место в дельте. `change/<id>`: открытое — ок, архивное — `ref-archived`, иначе висячая.
- **`delta-target-missing` / `delta-target-exists`.** Проверяются по ходу применения дельт изменения к основным спекам: MODIFIED/REMOVED/RENAMED FROM — на имя, которого нет на этом шаге и нет в ADDED другого открытого изменения; ADDED — на имя, которое на этом шаге уже есть. Сравнение имён точное, как в OpenSpec. Архивные изменения не проверяются.
- **`delta-overlap`.** Две дельты разных открытых изменений с одной capability и одним именем (для RENAMED — FROM). Предупреждение получает каждая такая дельта, `related` — дельты других изменений (D19).
- **`address-collision`.** Проверяется в основных спеках и в картине каждого открытого изменения; одна и та же пара имён сообщается один раз — на втором по порядку элементе, `related` — первый.

### Реестр решений (M3)

Решения — расширение формата, в OpenSpec их нет; корень без папки `decisions/` проверяется как раньше (D24).

- **Где.** `<корень>/decisions/<id>.md`, без вложенных папок; `id` — имя файла без `.md`, поэтому дубликатов в корне нет. Общие решения монорепо — в любом корне или в отдельном корне из `speclint.json`; в M5 общие решения публикуются отдельным репозиторием, то есть ещё одним пространством.
- **Формат.** Front-matter между строками `---` в начале файла, ключи `status: active | superseded | revoked` и `superseded-by: <id>` (решение того же корня). Обоснование — непустой раздел `## Rationale` или `## Обоснование`.

```markdown
---
status: superseded
superseded-by: 0012-paseto
---

# 0007 JWT для сессий

## Rationale

…
```

- **Ссылка** `spec:[пространство:]decision/<id>` разрешается по общим правилам адреса, в том числе в другой корень по пространству. Нет решения — `ref-dangling`. `superseded` или `revoked` — `decision-inactive-ref`: для заменённого сообщение называет цепочку замен до первого не заменённого решения (или до несуществующего id), `related` — файлы замен. Ссылки из самих файлов `decisions/` на неактивные решения не ошибка: реестр ссылается на свою историю (D26).
- **Реестр.** `decision-status-invalid`, `decision-no-rationale`, `decision-supersede-missing`, `decision-supersede-cycle` — на строке 1 файла решения. Цикл сообщается на каждом решении цикла (D27).
- Метки в тестах (M4) разрешают `decision/<id>` тем же кодом.

### Покрытие (M4)

- **Тестовые файлы.** Без `tests` в `speclint.json` — по конвенциям (D28), пути относительно репозитория:

| Язык | Тестовый файл |
|---|---|
| Kotlin/Java | `.kt`, `.kts`, `.java` под `src/<…>test/` или `src/<…>Test/` (`src/test`, `src/androidTest`, `src/integrationTest`); `*Test.kt`, `*Tests.kt`, `*IT.kt` и то же для `.java` где угодно |
| TypeScript/JS | `*.test.*`, `*.spec.*` (`.ts`, `.tsx`, `.js`, `.jsx`, `.mts`, `.cjs` …); любой `.ts`, `.tsx`, `.js`, `.jsx` … под `__tests__/` |
| Swift | `.swift` под папкой, чьё имя кончается на `Tests` (`Tests/`, `AppTests/`) |
| Python | `test_*.py`, `*_test.py`; любой `.py` под `test/` или `tests/` |
| Go | `*_test.go` (M9, D51) |

  `tests` — список glob-шаблонов (`**` — любые папки, `*` — часть имени, `?` — символ) и заменяет конвенции целиком. Папки, начинающиеся с `.`, и `node_modules`, `build`, `dist`, `out`, `target`, `Pods`, `Carthage`, `DerivedData`, `venv`, `__pycache__` не читаются никогда, и с `tests` тоже.
- **Метка** — токен `spec:` по общей разметке в любой строке тестового файла; язык не важен. Метка без пространства, чьей capability нет ни в одном корне репозитория и ни в одном манифесте зависимости, меткой не считается: ни ошибки, ни покрытия (D46). Так строки вроде `"spec:alpha"` — ID узла графа в `spekhq/spek` — не дают `test-ref-dangling`; опечатка в требовании или сценарии существующей capability и метка в соседний корень без пространства — по-прежнему ошибка, а опечатка в самой capability — ошибка `test-ref-dangling` с подсказкой, если capability метки отличается от известной не больше чем на две буквы (расстояние Левенштейна ≤ 2 по первым сегментам адреса, D49): `spec:serch/find-items` → «похоже на spec:search».
- **Корень теста** (D29). Один корень — все тесты его. Несколько — корень, чья родительская папка — ближайший предок файла (`services/auth/openspec` владеет `services/auth/**`). Тест вне всех корней обязан писать адрес с пространством, иначе `test-ref-dangling` «тест вне корней».
- **Что видит метка** (D31) — основные спеки и картины всех открытых изменений: тест пишут до архивации. Подсказки RENAMED, архив и решения — как у ссылок.
- **`test-ref-dangling`** (D32) — любая неразрешённая метка: висячая, в архив, на заменённое или отменённое решение; сообщение — как у ссылки. Внешний адрес — по манифесту (M5): `dependency-missing` и `ref-external-unchecked` — как у ссылок.
- **`scenario-untested`** — сценарий основных спек, на который нет метки ни сценария, ни его требования: метка требования покрывает все его сценарии (D30), метка capability — нет. Сценарии открытых изменений тестов не требуют до архивации (D31). Предупреждение — на строке сценария. Если на корень нет ни одной метки (ни своей, ни из `marks` загруженных манифестов), вместо предупреждения на каждый сценарий — одна находка уровня info на папке корня, строка `null`: «сценариев без теста: N; в тестах нет ни одной метки на этот корень» (D45). Так репозиторий, где покрытие ещё не размечено, не тонет в тысячах предупреждений; с первой меткой правило работает по сценариям.

### Шаги (M6)

Вторая ступень покрытия (D7): тест не только ссылается на сценарий, но и несёт его шаги дословно в строковых литералах.

- **Шаг** (D40) — строка тела сценария, которая после снятия маркера списка (`- `, `* `, `+ `), всех `**` и пробелов по краям начинается с `GIVEN`, `WHEN`, `THEN`, `AND` или `BUT` (заглавными, целым словом). `- **WHEN** the user enters a valid password` → `WHEN the user enters a valid password`. Прочие строки тела (пояснения) — не шаги.
- **Совпадение** — шаг точно равен литералу после обрезки пробелов по краям литерала: регистр и пробелы внутри важны. При промахе сообщение называет «похожую строку» — литерал, равный шагу без учёта регистра, `ё/е` и повторных пробелов, как в Clear `trace`.
- **Чьи литералы** (D42). Литералы всех тестовых файлов, где есть метка сценария или его требования, складываются; шагу достаточно найтись в одном. Метка требования требует шаги всех его сценариев. К какому тесту внутри файла относится метка, не важно: сравнивается весь файл.
- **Что проверяется** — сценарии основных спек, на которые есть метка, и сценарии зависимостей по манифесту формата `2` (D43). Сценарии открытых изменений шагов не требуют, как и тестов (D31). Сценарий без меток — забота `scenario-untested`, а не этого правила.
- **Находка** — предупреждение на строке сценария, по одной на недостающий шаг, `related` — метки: сначала требования, потом сценария. Для сценария зависимости — на файле манифеста, строка `null`, адрес с пространством.
- Литералы читаются только из тестовых файлов с меткой (D44).

**Лексер строк** (D41) — один на все языки, режим по расширению файла: Python (`.py`), JS/TS (`.js`, `.ts`, `.jsx`, `.tsx`, `.mjs`, `.cts` …), остальные (Kotlin, Java, Swift, Go). У `.go` строка в обратных кавычках — сырая многострочная, экранирование не раскрывается (D51).

| | Python | JS/TS | Kotlin/Java/Swift |
|---|---|---|---|
| Комментарии (не литералы) | `#` до конца строки | `//`, `/* */` | `//`, `/* */` (вложенность не учитывается) |
| Однострочные | `"…"`, `'…'` | `"…"`, `'…'` | `"…"`, `'…'` |
| Многострочные | `"""…"""`, `'''…'''` | `` `…` `` | `"""…"""` |
| Берутся как написаны | префиксы `r`/`f`/`b`/`u` и сочетания; у `r` экранирование не раскрывается | `${…}` в шаблоне | `$x`, `${…}`, `\(x)`; сырые строки Swift `#"…"#`, `##"…"##`, `#"""…"""#` |
| Не литерал | | регулярные выражения `/…/` | имена в обратных кавычках `` `…` `` |

- Экранирование `\"`, `\'`, `\\`, `` \` `` раскрывается в символ, прочие (`\n`, `\t`, `\u…`, `\$`) остаются как написаны.
- Интерполяция не вычисляется: литерал с ней совпадёт с шагом, только если шаг содержит тот же текст.
- Однострочная строка, не закрытая до конца строки, отбрасывается, разбор идёт дальше со следующей строки; многострочная, не закрытая до конца файла, отбрасывается.
- Регулярное выражение JS/TS — `/` в начале файла или после `( , = : [ ! & | ? { } ;` или `return` (пробелы между не важны); оно идёт до `/` вне `[…]` в пределах строки. Это эвристика, как у подсветки синтаксиса: на `microsoft/vscode` без неё сбивался разбор ~7% тестовых файлов.
- Не поддержано (отложено): вложенные шаблоны внутри `${…}` (`` `a ${f(`b`)}` ``) — сбивают разбор до следующей обратной кавычки; вложенные `/* */` Kotlin и Swift.

Внутрифайловые проверки `openspec validate` (дубликаты в разделах, конфликты разделов, непарные RENAMED, потеря сценариев) speclint не повторяет — см. [openspec-format.md](openspec-format.md#что-уже-проверяет-openspec-validate).

## Конфигурация

Не нужна для одного корня `openspec/`. Файл `speclint.json` в корне репозитория:

```json
{
  "roots": [
    { "path": "services/auth/openspec", "space": "auth" },
    { "path": "services/billing/openspec", "space": "billing" }
  ],
  "tests": ["**/src/test/**", "**/*.test.ts", "**/Tests/**/*.swift", "**/tests/**/*.py"],
  "dependencies": {
    "identity": { "manifest": "speclint/identity.manifest.json", "version": "1.4.0" },
    "legacy": { "unchecked": true }
  }
}
```

- `roots` — M2: непустой список; `path` — папка корня относительно репозитория, `space` обязательно, `[a-z0-9-]+`, уникально. Иначе — код `2` «нечитаемая конфигурация»; несуществующий `path` — код `2` «корень не найден». С конфигурацией проверяются только перечисленные корни, `<путь>/openspec` не подразумевается (D21).
- Каждый корень проверяется правилами M1 отдельно: дельты, `delta-overlap` и коллизии адресов — внутри своего корня. Ссылка `spec:<space>:…` с пространством другого локального корня разрешается в его основных спеках (дельты своего изменения к чужому корню не применяются); подсказки RENAMED, `ref-archived` и «есть в открытом изменении» берутся из изменений того корня (D22).
- `tests` — M4; glob-шаблоны тестовых файлов, заменяют конвенции (D28). Не список строк — код `2`.
- `roots[].class`, `roots[].uses` — M10: корень как ограниченный контекст; `class` — `core`, `supporting` или `generic` (в `core` `scenario-untested` — error, D58), `uses` — пространства корней или `dependencies`, на которые контексту можно ссылаться (D55, D56).
- `textChecks`, `behaviourChecks` — M11: строки, по которым тест под меткой считается чтением исходников или проверкой поведения; тело теста — от метки до следующей строки с нулевым отступом, кроме закрывающих скобок (D59).
- `rules` — M9; `{ <правило>: off | error | warning | info }`: `off` выключает правило, уровень заменяет уровень по умолчанию, код возврата считается после замены (D52). Неизвестное правило или уровень — код `2`.
- `dependencies` — M5; ключ — пространство, значение — `{ manifest, version }` (путь к локальной копии манифеста относительно репозитория и зафиксированная версия) или `{ unchecked: true }` (пространство сознательно не проверяется). Иначе — код `2`.

## Манифест (M5)

Мультирепо без соседних чекаутов (D6): репозиторий-поставщик на релизе собирает манифест командой `speclint manifest . --release 1.4.0 > identity.manifest.json` и публикует его любым своим артефактом (npm, Maven, файл релиза — speclint об этом не знает). Потребитель кладёт копию в свой репозиторий (`speclint/identity.manifest.json`) и фиксирует версию в `dependencies`; обновление копии — явный шаг, вручную или скриптом CI, diff копии виден в PR как у lock-файла (D34). Проверка читает только локальные файлы, сети нет.

```json
{
  "speclint": 2,
  "version": "1.4.0",
  "roots": [
    {
      "space": "identity",
      "capabilities": ["auth"],
      "requirements": [
        { "address": "auth/legacy-login", "status": "removed", "change": "drop-legacy" },
        {
          "address": "auth/log-in",
          "status": "active",
          "name": "Log In",
          "scenarios": [{ "address": "auth/log-in#valid-password", "name": "Valid password", "steps": ["WHEN the password is valid", "THEN the user is signed in"], "covered": true }]
        },
        { "address": "auth/login", "status": "renamed", "change": "rename-login", "to": "auth/log-in" }
      ],
      "changes": [{ "id": "add-2fa", "archived": false }, { "id": "rename-login", "archived": true }],
      "decisions": [{ "address": "decision/0007-jwt", "status": "superseded", "supersededBy": "decision/0012-paseto" }]
    }
  ],
  "marks": ["web:checkout/pay#card"]
}
```

(Выше — сокращённо; настоящий вывод — JSON с отступом 2, каждый элемент массива на своей строке.)

- `speclint` — версия формата, сейчас `2`: с M6 сценарий несёт `steps` — шаги по правилу [Шаги](#шаги-m6), уже без маркеров. Формат `1` (M5) — без `steps`; читаются оба, по манифесту формата `1` шаги сценариев зависимости не сверяются (D43). `version` — из `--release`.
- `roots` — все корни репозитория (M2), у каждого обязательно пространство. Правка черновика M0: был один `space` на манифест (D36).
- `requirements` — требования основных спек (`active`, с именем и сценариями) и история архивных изменений: `removed` и `renamed` с адресом по старому имени, изменением и новым адресом. Требования открытых изменений не публикуются, сами открытые изменения — только id.
- `covered` — сценарий покрыт метками тестов этого репозитория (метка требования покрывает все его сценарии, D30).
- `marks` — метки тестов этого репозитория на чужие пространства, как написаны: по ним другие репозитории узнают, что их сценарии покрыты здесь.
- Детерминизм: массивы упорядочены по адресу или id сравнением кодовых точек (история и активное требование с одним адресом — по `status`), порядок ключей фиксирован; diff манифестов двух версий читается построчно.

**Проверка с зависимостями** (D37–D39).

- Манифест читается для каждого пространства с `manifest`: нет файла — у ссылок `dependency-missing` «манифест X не найден»; в файле нет пространства — `dependency-missing`; файл не JSON, `speclint` не `1` и не `2` или `version` не совпадает с зафиксированной — код `2`.
- Внешний адрес `spec:<space>:…` (и метка в тесте) разрешается в манифесте теми же правилами, что локальный: `ref-dangling`, подсказка RENAMED, `ref-archived` (удалённое требование, архивное изменение), `decision-inactive-ref`, для меток — `test-ref-dangling`. Сообщение кончается на `; зависимость <space> <version>`, `related` пуст: строк в манифесте нет. Пространство не объявлено — `dependency-missing`; объявлено `unchecked` — `ref-external-unchecked` (info).
- `scenario-untested-anywhere` (решение пользователя: все известные сценарии): сценарий покрыт, если на него есть метка в тестах этого репозитория, `covered` в манифесте его репозитория или метка в `marks` любого загруженного манифеста. Если загружен хоть один манифест, непокрытый сценарий своего корня получает `scenario-untested-anywhere` вместо `scenario-untested`; непокрытый сценарий зависимости — `scenario-untested-anywhere` на файле манифеста, строка `null`, но только если этот репозиторий сам на него опирается: ссылка или метка разрешается в этот сценарий, его требование или capability (D48). Остальные непокрытые сценарии поставщика — забота поставщика, потребитель их не повторяет.
- Поставщик видит покрытие у потребителей, если объявит их манифесты в своих `dependencies`, как любую зависимость: `marks` потребителя засчитываются его сценариям, а сценарии потребителя поставщику не сообщаются, пока он на них не ссылается (D48).
- `summary.files` включает прочитанные манифесты.
- `scenario-steps-missing` по сценарию зависимости — если манифест формата `2` и на сценарий есть метка в тестах этого репозитория (M6).
